## 2. 逐条详述

### 2.1 🟡 登录限流可被伪造 `X-Forwarded-For` 绕过（`api/deps.py`）

**问题**：`_client_ip()` 无条件采信 `X-Forwarded-For` 的第一跳。

```python
# 旧实现
forwarded = request.headers.get("x-forwarded-for", "")
if forwarded:
    return forwarded.split(",")[0].strip()
return request.client.host if request.client else "unknown"
```

**为什么这是缺陷**：`X-Forwarded-For` 是**请求头**，任何客户端都能自己写。
而登录限流恰是**按来源 IP 建桶**的（`get_limiter("login")` + `ip:{addr}`）：

```bash
# 攻击者视角：每次请求换一个假 IP，就拿到一把全新的桶
for i in $(seq 1 10000); do
  curl -s -H "X-Forwarded-For: 10.$((RANDOM%256)).$((RANDOM%256)).$((RANDOM%256))" \
       -d '{"email":"admin@example.com","password":"guess'$i'"}' \
       http://target/api/v1/auth/login
done
```

结果：`RATELIMIT_LOGIN_BURST=5 / PER_MINUTE=10` 完全不起作用，防撞库只剩
「账号锁定（5 次 / 15 分钟）」与「失败 3 次后强制图形验证码」两道——
而账号锁定本身又是**按账号**的，攻击者可以拿一个账号打满 4 次再换账号，
横向扫多个账号时几乎不受阻。

**修法**：默认**完全不信任**该头，只信任"直连对端确实是我们自己的代理"的情况。

```python
peer = request.client.host if request.client else "unknown"
trusted = get_config().trusted_proxies
if not trusted:
    return peer                     # 默认：直连部署，用 TCP 对端地址
if not ("*" in trusted or peer in trusted):
    return peer                     # 来自非受信对端 → 伪造的头一律忽略
return request.headers.get("x-forwarded-for", "").split(",")[0].strip() or peer
```

- 新增配置 `TRUSTED_PROXIES`（逗号分隔，空 = 不信任任何代理）。
- `production_warnings()` 增加一条：`TRUSTED_PROXIES=*` 会告警（等于放弃这层防护）。
- `.env.example` 写了「反代部署必须配置，否则所有访客会被算成同一 IP」的提醒——
  这是把安全默认值带来的**运维代价**显式说清楚，而不是藏着。
- 回归测试：`test_xff_is_ignored_by_default` / `test_xff_honored_only_from_trusted_proxy` /
  `test_xff_wildcard_trusts_all`。

### 2.2 🟡 同一 SQLite 文件的多 store 未共享写锁（`store/base.py`）

**问题**：`BaseStore.__init__` 里 `self._write_lock = threading.Lock()` 是**实例级**的，
而类文档写的是「子类共享同一个库文件与写锁」——**文档与实现不符**。

**为什么这是缺陷**：`deps.py` 里四个 store 指向**同一个** `CONSOLE_DB_PATH`：

```
ConversationStore(console.db)   ─┐
TicketStore(console.db)         ─┤  四个实例 = 四把互不相干的锁
FeedbackStore(console.db)       ─┤  同时写同一文件的同一 SQLite 单写者临界区
AnswerCacheStore(console.db)    ─┘
```

一次聊天会写会话 + 消息 + 缓存，一次工单操作会写 tickets——两条链路并发时
**没有任何互斥**，只能靠 SQLite 的 `busy_timeout=10s` 兜底；一旦排队超过 10s
就直接 `database is locked`（一次 500，或触发降级转人工）。

**修法**：写锁改为**按库文件路径注册**，同文件必得同一把锁。

```python
_write_locks: dict[str, threading.Lock] = {}
_write_locks_guard = threading.Lock()

def _write_lock_for(db_path: Path) -> threading.Lock:
    key = str(db_path.resolve())
    with _write_locks_guard:
        lock = _write_locks.get(key)
        if lock is None:
            lock = threading.Lock()
            _write_locks[key] = lock
        return lock
```

判定性断言（不依赖时序）：`test_stores_on_same_db_share_one_write_lock` 断言四个 store 的
`_write_lock` 是**同一个对象**；`test_different_db_files_do_not_share_lock` 断言不同库文件**不**共享
（避免无关的库互相阻塞）。另有一条真实的交叉写入冒烟测试。

### 2.3 🟡 LLM 健康判定会永久卡在"不可用"（`common/resilience.py`）

**问题**：`snapshot()["ok"]` 等价于 `_consecutive_failures == 0`，而失败计数**只能被下一次成功调用清零**——
没有任何定时探针。

**为什么这是缺陷**：`/readyz` 用这个 `ok` 决定 200/503。
于是「一次偶发超时」之后如果**没有新流量**（夜间、低峰、刚发布），
`/readyz` 会**一直 503**：

- K8s 会把其实健康的 Pod 永久摘出负载均衡（直到有人手动发一次问答把它"治好"）；
- 监控会长期误告警，运维逐渐学会"忽略这个告警"——比告警本身更糟。

同时模块文档写的是「最近 5 分钟内有成功即视为健康」，**实现里根本没有时间维度**，
属文档与实现不一致。

**修法**：引入**陈旧窗口**，把"真的坏了"和"信息过期了"分开。

```python
HEALTH_STALE_SECONDS = 300.0     # 失败记录超过该时长且期间无新调用 → 信息陈旧

stale = (consecutive_failures > 0 and last_failure_at is not None
         and now - last_failure_at > stale_after_seconds)
healthy = consecutive_failures == 0 or stale
```

- `snapshot()` 新增 `stale` 字段：运维能区分「现在真的坏了」与「这是没流量的旧结论」。
- `quota_exhausted` 同样加了陈旧判定——三天前的一次欠费不该让指标一直亮红灯。
- 回归测试：新鲜失败 → `ok=False, stale=False`；窗口内放过 → `ok=True, stale=True`；
  成功调用后 → `ok=True, stale=False`。

> 取舍（工程权衡）：窗口型健康判定**弱化了"真的长期故障"的敏感性**（无流量时不再报 503）。
> 这里选择它的理由是：`/readyz` 的语义是「**能不能接流量**」，而"没有证据表明它坏了"
> 比"三天前的证据表明它坏了"更贴近当下事实。要更严格就该加**主动探针**（定时发一次
> 最小请求），那是下一步而不是这一版——因为主动探针会产生真实费用与延迟，
> 需要显式的预算控制。

### 2.4 🟡 知识库更新后旧答案仍在缓存里（`api/v1/ops.py`）

**问题**：问答缓存的键是 `sha1(language + 规范化问题)`，**不含知识库版本**。

**为什么这是缺陷**：运维在控制台改完商品文档 / 政策文档 → 触发重新入库 →
**一小时内**（`CONSOLE_CACHE_TTL_SECONDS`）同样的老问题仍然命中**改之前**的答案。
用户（验收方）看到的现象是：

> "我明明把文档从『30 天可退』改成『14 天可退』了，问它还是说 30 天。"

这几乎必然被误判成"检索没生效 / 向量库没更新"，然后浪费大量时间往检索链路里查。

**修法**：重新入库确实发生变更（有上传或删除）时，**自动作废问答缓存**；
纯跳过的一轮不动缓存（避免白白清空热缓存）。抽成可测的函数 `_invalidate_answer_cache(report)`。

```python
if not (getattr(report, "uploaded", None) or getattr(report, "deleted", None)):
    return 0                     # 没有任何变更 → 不动缓存
cache = get_answer_cache()
return cache.clear() if cache is not None else 0
```

- 三条回归测试：有变更 → 清空且返回条数；无变更 → 保留；缓存被关闭（`None`）→ 不抛错。

### 2.5 🟢 `PRAGMA foreign_keys` 实际未生效（`store/base.py`）

**问题**：`foreign_keys` 是**连接级**开关（SQLite 默认 OFF），原实现只在 `_init_schema`
那**一条**连接上执行，之后每个业务连接都带着默认的 OFF。

**为什么算缺陷**：当前 schema 还没写外键，所以现在没有可见症状——
但这是**潜伏缺陷**：一旦后续给（例如）`ticket_replies.ticket_id` 加上
`REFERENCES tickets(ticket_id) ON DELETE CASCADE`，约束会**静默失效**，
删工单时留下孤儿回复，而开发者会以为数据库帮他兜住了。

**修法**：`_connect()` 里每条连接都 `PRAGMA foreign_keys=ON`。测试直接断言 PRAGMA 返回值。

### 2.6 🟢 限流参数改了不生效（`common/ratelimit.py`）

**问题**：`get_limiter(name, capacity=..., per_minute=...)` 只在**首次创建**时应用参数：

```python
limiter = _limiters.get(name)
if limiter is None:
    limiter = RateLimiter(capacity=capacity, per_minute=per_minute)   # 之后传入的值被丢弃
    _limiters[name] = limiter
return limiter
```

**为什么算缺陷**：运维把 `RATELIMIT_CHAT_PER_MINUTE` 从 30 调到 10，重启后
**依然按 30 放行**——配置里写着 10，实际行为不是 10。"配置说了不算"是最消耗信任的一类 bug。

**修法**：新增 `RateLimiter.matches()`，参数不一致即重建。

```python
if limiter is None or not limiter.matches(capacity=capacity, per_minute=per_minute):
    limiter = RateLimiter(capacity=capacity, per_minute=per_minute)
    _limiters[name] = limiter
```

测试：改参数 → 返回**新实例**且新参数生效；参数不变 → **复用同一实例**（不白白丢掉已有令牌状态）。
